# 資料來源是怎麼設計的

這一段是原作者（[beybladehunter/LineDraw-Android](https://github.com/beybladehunter/LineDraw-Android)）的設計，全自動版沒有改動；這份文件是讀程式碼整理出來的說明。

相關程式都在 `app/src/main/java/com/linedraw/app/data/`：

| 檔案 | 負責什麼 |
| --- | --- |
| `CatalogSource.kt` | 下載來源網頁、解開短網址 |
| `DrawParser.kt` | 把 HTML 解析成一筆筆抽選活動 |
| `DrawSchedule.kt` | 從時間文字解析抽選起訖時間 |
| `Models.kt`（`LinkPolicy`） | 網域白名單、活動身分識別 |
| `Repository.kt`（`sync`） | 串起整個同步流程並寫入資料庫 |
| `ProductCatalog.kt` | 商品型號歸類，供篩選使用 |

## 來源只有一個：Funbox 的公開網頁

App 沒有自己的後端或 API，直接抓 <https://uxux11.github.io/funbox-line/> 這個放在 GitHub Pages 上的靜態網頁（由別人維護），把 HTML 當資料庫來讀。

## 同步流程

1. **下載網頁**：一般的 HTTP GET，逾時 15 秒，不跟隨轉址，回應不是 200 就算失敗，內容超過 2 MB 就拒收。
2. **解析 HTML**：用 jsoup 找 `#page-draws .draw-store`，每個區塊是一間門市，讀出：
   - 店名（`.draw-store-name`）、縣市（`data-draw-city`）
   - 時間文字（`.draw-start`，例如「抽選/購買時間：2026/10/08 11:00 ~ 2026/10/09 21:00 止」）
   - 每一列商品（`.draw-item`）的商品名、連結（`data-draw-href`，是 `lin.ee` 短網址）、來源 ID（`data-draw-id`）
3. **解析時間**：只認「抽選」那一段的起訖時間，以台北時區換算；後面的「使用期限」不會被當成抽選結束時間。
4. **解開短網址**：每個 `lin.ee` 連結逐一追轉址（最多 6 跳、一次 4 條並行、每條 15 秒），直到拿到真正的 LINE 優惠券網址 `liff.line.me/<頻道>/c/<優惠券ID>`。
5. **寫入本機資料庫**：舊清單整批標成封存，再寫入新清單，在同一個交易內完成。

## 設計重點

| 設計 | 做法 | 解決什麼問題 |
| --- | --- | --- |
| 活動身分用優惠券 ID | 解開短網址後，用「頻道＋優惠券 ID」當活動的唯一識別 | 同一個活動被貼成兩個不同短網址時不會抽兩次；抽過的紀錄也掛在這個 ID 上 |
| 每次同步都重新解短網址 | 即使 HTML 沒變也重解 | 同一個短網址可能被店家改指向新一期活動 |
| 來源缺 ID 時自己產生 | 用店名、網址、商品、開始時間算雜湊 | 來源漏填 ID 不會讓整份清單同步失敗（0.1.3 修的就是這個） |
| 網域白名單 | 只接受 `lin.ee`、`liff.line.me`、`line.me` 的 https 連結 | 來源網頁被竄改也不會被導去別的網站 |
| 嚴格驗證、寧可不更新 | 找不到抽選區、店名缺漏、ID 重複、筆數超過 5000 都直接失敗 | 來源改版或壞掉時保留上次的有效清單，不寫進半套資料 |
| 清單有效期 24 小時 | 超過就要求先同步才能開始 | 避免拿過期清單去抽 |
| 商品歸類 | 用正規表示式抓 `BX-xx`、`UX-xx`、`CX-xx` 型號當分類鍵 | 同型號不同寫法歸在一起，篩選才準 |

## 哪些活動會被排入抽選

一筆活動要同時符合這些條件才算「可抽選」：

- 有明確的開始與結束時間，而且現在落在期間內。
- 沒有被封存（還在最新一次同步的清單裡）。
- 本機沒有這個活動的紀錄（沒抽過、沒手動標記完成）。

時間解析不出來的會歸到「時間未確認」，不會被自動抽；還沒到開始時間的是「尚未開始」。

## 這個設計的弱點

- **完全依賴別人的網頁結構**：Funbox 那頁只要改 CSS class 名稱或版面，同步就會失敗（會保留舊資料，但拿不到新活動）。
- **時間靠文字解析**：時間寫法一變，活動會落到「時間未確認」。
- **只有 Funbox 一個來源**：原作者的 VIP 版另外支援陀螺獵人官網，這個公開版沒有。

## iPhone 腳本走的是另一條路

[`ios-mirroring/`](../ios-mirroring/) 沒有重做這套同步，而是直接利用 Funbox 網頁自己的「自動連抽」功能：清單、順序、哪些抽過（存在瀏覽器的 localStorage）都交給那個網頁管，Mac 腳本只負責在 LINE 裡按抽獎和關視窗。

好處是不用維護解析程式；代價是沒有本機紀錄，也沒有短網址去重。

## 想接別的來源時

要換的只有「下載」（`CatalogSource`）和「解析」（`DrawParser`）兩塊，後面的身分識別、白名單、資料庫都能沿用。`DrawCatalog` 目前寫死只有 `FUNBOX` 一個來源，新增來源要從那裡開始。
